# ADS 未响应审查与优化方案

审查日期：2026-10-30（Asia/Shanghai）。基于当前工作区文件、用户数据目录日志、进程状态及离线测试。当前仓库已有大量未提交修改，本次未改运行代码或 ADS 设计，也未终止现场进程。

## 结论

首要问题是：Agent 可以把长时间数值计算交给 ADS 主线程上的 `run_python` 执行。工具请求的超时仅结束请求等待，不能结束正在执行的 Python；聊天停止也没有接通普通 ADS 工具作业的取消。长计算期间，界面、计时器和停止按钮都无法正常处理事件。

这是有实际日志和代码共同支持的阻塞路径。尚未抓取线程栈或原生转储，因此不能认定所有未响应事件都只有这一原因，也不能把当前现场判定为互斥锁死锁。

## 2. 调用链与问题分级

```text
聊天面板 ChatWorker（网络线程）
  → 后端 Turn → tools.call → HTTP /execute
  → submit 入队，HTTP线程等待
  → ADS主线程 QTimer 每50ms调用 pump
  → handler(args, ctx)
      ├─ run_python：主线程 exec，执行完成才返回
      ├─ build_schematic：布局、走线、数据库修改、验证同步完成
      └─ run_simulation：主线程生成网表，再 defer 到仿真线程
```

### P0：长计算在主线程，且任意 Python 默认开启

- `addon/ads_agent/toolserver.py:608` 的 `pump()` 在主线程执行，`:678` 同步调用处理器。
- `addon/ads_agent/ads_ops.py:7211` 的 `run_python()` 直接 `exec(...)`，没有执行期限检查、协作取消或进程隔离。
- `addon/ads_agent/panel.py:1512` 的 Python 选项默认勾选。
- 即使计算函数内部释放GIL，承载该函数的GUI线程仍在等函数返回，不能回到Qt事件循环。

**影响：** 纯计算、文件扫描、长循环、直接调用仿真SDK都可能冻结ADS；不断增加网络超时只会延长等待。

### P0：超时不是执行终止，聊天取消未覆盖当前工具

- `backend/tools.py:1019` 给 `run_python` 600秒等待时间；发给ADS的是630秒。
- `addon/ads_agent/toolserver.py:562` 的 `submit()` 超时后仅标记 `timed_out` 并抛错，处理器继续执行。
- `backend/server.py:1044` 的 `/chat/cancel` 调用 `Turn.cancel()`；`backend/agent.py:831` 仅设置轮次事件。
- 普通工具调用 `backend/agent.py:1292` 附近未传递取消事件或预登记作业ID；`tools.call()` 在内部生成ID。
- ADS端 `request_cancel()` 已支持跳过排队作业，但执行中只是写标记；`run_python()` 不读取该标记。
- 面板的停止按钮和耗时计时器都在同一GUI事件循环中，界面已阻塞时甚至无法发出停止请求。

**影响：** 用户看到超时或停止后，旧作业可能还活着；新请求可能排在旧作业后面。现有重复失败保护不能识别所有改写参数后的重复请求，也不能替代作业状态核查。

### P1：pump只有作业数量预算，没有时间预算

- 默认每次最多16个作业（`toolserver.py:317`），不限制单次占用毫秒数。
- 一个作业就能卡住78秒；把数量改成1只能降低连续作业积累的延迟。
- 队列容量检查是 `qsize()` 后再 `put()`，不是原子的有界入队；并发提交时可能越过容量检查。

### P1：建图、数据集读取仍有主线程重活

- `ads_ops.py:5790` 附近，建图调用自动布局、走线规划后继续同步修改数据库、保存和复核。
- `ads_ops.py:6723` 的 `read_traces()` 在处理器内展开DataFrame、逐点转换、筛选；先物化完整数据再降采样，`max_points`不能限制前期内存峰值和转换成本。
- `ads_ops.py:6342` 的仿真在defer前仍需审查设计、生成网表和解析模型依赖。这些阶段也应单独计时。
- 仿真后台线程虽已实现，但每次直接新建daemon线程，没有看到全局仿真并发额度，也未在此层暴露可取消的仿真子进程句柄。

这些是代码层风险，尚无证据证明它们造成了当前14:53:44这一现场。

### P2：长会话UI仍有全量工作

- 正文和思考增量已经约8Hz节流，不能笼统认定“每个token都全量重绘”。
- 但 `panel.py:4693` 的活动刷新仍调用 `_rebuild()` 和同步保存；`:4373` 的重建会清空并重建所有聊天行。
- `panel.py:1776` 同步保存整个会话；`project_store.py:57` 进行JSON序列化、读取旧文件、备份、fsync和替换，文件占用时还会重试等待。
- 当前会话文件约693 KB；这提示后续规模测试价值，不能仅凭文件大小认定它已造成卡死。

## 3. 建议实施顺序

### 阶段A：先切断已知阻塞入口

1. 在设置里关闭“允许执行 ADS Python”，作为恢复后的临时缓解；这会限制依赖任意脚本的探索能力。`sim_off_main_thread=true` 保持开启。不要期待关闭选项能中止已经运行的脚本。
2. 新增后端 `run_compute` 工具，用受管理的独立子进程运行纯数值计算。输入为JSON或已授权数据资产引用，输出为结构化结果、日志和产物引用。通过环境和工具接口约束避免把GUI数据库对象带过去；它不是任意代码安全沙箱。
3. 数据读取和优化拆开：短工具读取ADS数据快照；独立进程完成匹配、拟合、搜索；短写入工具应用结果；再按现有门禁仿真验证。
4. 任意 ADS Python 改为默认关闭，保留兼容入口供短脚本使用。提示词与AST检查可降低误用，但无法提供可靠的硬超时；不要把它们视作主线程执行隔离。
5. 将Touchstone解析封装为确定性工具，按文件选项行处理单位及DB/MA/RI格式，避免把同类解析反复交给脚本猜测。

### 阶段B：把超时、取消和作业身份接通

1. 后端派发前生成job_id，登记 `turn_id → job_id → worker_pid`；排队、执行、取消中、成功、失败、超时分开记录。
2. `/chat/cancel` 同时设置轮次事件并请求取消当前作业；排队任务直接跳过，独立计算进程按宽限期终止并回收，数据库事务在明确安全边界退出。
3. 对计算进程与仿真进程分别实现进程树所有权、Windows隐藏启动、超时清理、日志排空和退出等待。只终止本插件拥有的worker，不终止ADS宿主。仿真取消先以隔离用例确认SDK和进程树行为。
4. 请求超时后仍保留作业状态，未确认旧写入作业结束前禁止自动重试同一操作。写入增加请求幂等标识和目标设计版本检查。
5. SSE读取实现可取消的连接生命周期，停止后能及时退出读取，而不是只设置标记再等下一段数据或1800秒socket超时。

### 阶段C：缩短主线程事务并限制资源

1. `pump_max_jobs` 先降为1作为辅助措施，再增加约5–10ms软时间预算；预算只能阻止开始下一个作业，无法抢占当前处理器。
2. 自动布局、走线规划、几何比较等纯计算移到worker。主线程提取普通数据快照，worker返回计划，主线程验证工作区和设计版本后应用。
3. 数据库写入按ADS事务契约设计可中止边界；不能简单在未完成事务中反复 `processEvents()`，避免重入和用户操作看到半成品。单次不可拆原生调用仍需记录耗时和适用规模。
4. 队列使用原子有界 `put_nowait()`，限额区分排队任务与活跃后台任务；仿真默认单并发，后续按资源测量放宽。
5. 数据集文件在兼容环境的独立worker读取；按数据块缓存转换结果，预览和精确指标计算分开走受控输出。保留完整数据的来源和精确性标记。
6. UI只更新当前活动行；会话保存使用有序后台写入和合并提交，保留原子保存与备份。退出时刷新待保存快照，避免旧快照覆盖新状态。

### 阶段D：加入可定位卡顿的观测

- GUI QTimer维护独立心跳时间；`/health` 同时返回服务存活与GUI心跳年龄，避免HTTP服务能响应就被认为ADS界面正常。
- 心跳异常时由外部观察方标为“主线程疑似阻塞”；若进程内HTTP/GIL也不响应，由外部进程执行超时探测。
- 日志统一带 turn_id、job_id、线程、worker_pid、工具类型、入队/主线程开始/释放/计算结束/落盘时间。不要只在完成后记录总耗时。
- 下一次卡顿抓取线程栈；涉及原生调用时再采集Windows进程转储。当前审查未抓取，不用猜测补充调用栈。

Qt要求GUI对象在主线程访问，同时建议将耗时工作移出GUI线程；这里仍须遵守ADS数据库自身的线程契约。[Qt官方说明](https://doc.qt.io/qt-6/threads-qobject.html)。Python的 `Popen.communicate(timeout=...)` 超时不会自动杀死子进程，必须显式清理并回收。[Python官方说明](https://docs.python.org/3/library/subprocess.html#subprocess.Popen.communicate)。

## 5. 修复后的验收条件

| 场景 | 建议通过标准 |
|---|---|
| 30秒纯计算任务 | ADS持续可操作；GUI心跳常态目标<200ms，连续停顿>1秒计失败，记录测试机器和设计规模 |
| 计算中停止 | 1秒内确认取消请求；约3秒内worker退出或明确显示仍在清理；ADS不退出 |
| 计算到期 | 进程被回收、最终状态一致、没有遗留后代进程；产物明确标为部分结果或失败 |
| 普通聊天工具排队时停止 | 从turn_id追踪到作业，处理器未进入执行；不能只验证轮次标志位 |
| 长优化后应用结果 | 先验证设计版本，再写入新结果；工作区切换或版本变化时拒绝应用过期计划 |
| 仿真取消/超时 | 孤立测试电路中确认清理，仅结束所拥有仿真进程；现有设计和其他ADS实例不受影响 |
| 超时后重复发送 | 不重复执行未确认结束的写入；状态查询显示原job_id真实下场 |
| 建图及长会话 | 固定规模电路与100/1000条消息分别测主线程最大停顿、内存和保存耗时；不能仅看平均帧率 |

建议先完成阶段A与B，再处理布局和会话性能。仅调整超时、步数、pump数量或增加“正在执行”提示，均不能消除已经证实的主线程长计算路径。
