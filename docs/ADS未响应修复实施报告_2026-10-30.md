# ADS 未响应修复实施报告（2026-10-30）

对应审查文档：[`ADS未响应审查与优化方案_2026-10-30.md`](ADS未响应审查与优化方案_2026-10-30.md)。
本报告记录**本次实际落地的代码修改**、验证证据与剩余限制，不是再一份建议清单。

## 结论

1. **长计算已离开 ADS 主线程**：新增 `run_compute` 工具 + `backend/compute_worker.py`（独立子进程运行时）+ `backend/compute_manager.py`（排队/取消/预算/进程树回收）。数值优化、拟合、大规模搜索、纯数据处理跑在后端进程的子进程里，ADS GUI 主线程完全不参与。实测 60×60 L-BFGS-B 优化在 worker 内 0.81s 完成，结果与进程内同步基线在 1e-6 容差内一致。
2. **停止真的能停**：`job_id` 在派发**之前**登记，`/chat/cancel` 沿 `turn_id → job_id → worker_pid` 传播到计算管理器与 ADS 工具服务；排队作业取消后**一行用户代码都不跑**；运行中作业先如实标 `cancel_requested`，再按宽限期 → `terminate` → `taskkill /T /F`（仅本插件自己的 pid 树）回收。实测协作式取消 0.06s 退出、非协作热循环 1.07s 被终止、预算到期 3.10s 回收，均无孤儿进程。
   **仿真也能停了**（本轮新增）：`keysight.edatoolbox` 的 `run_netlist()` 既没有 timeout 也没有 cancel 参数（底层是一句 `subprocess.check_call`），我们改为在 `_execute` 处自己 `Popen` hpeesofsim，因此拿得到 pid：取消即终止、`sim_timeout` 到期即终止并标 `timed_out`，输出写文件不用管道所以不会写满互锁。**这是本插件接管子进程实现的，不是 SDK 的能力。**
3. **面板不再靠 socket 超时"发现"停止**：`ChatWorker.stop()` 会主动关掉本地读取 socket，读线程 2.5s 内退出（此前要等 15s keepalive 或最坏 1800s），并新增 `cancel_requested` 事件的"已请求取消 / 仍在执行"两阶段反馈。
4. **"HTTP 请求结束"不再被当成"执行结束"**：等待超时只结束等待，作业真实状态仍可查询；超时/取消后不自动重做未确认的写入；部分结果标 `partial=true`，不再谎报完整成功。
5. **主线程重活按证据处理**：`read_traces`/`read_dataset` 按数据块缓存 DataFrame；聊天活动行改就地刷新（不再 `chat.clear()` 全表重建）；会话保存改合并写（500ms 单发定时器）+ 立即落盘时机保留 + 关闭前强制 flush。布局/走线规划经 A/B 实测确认**典型规模不需要搬走**（见 §6.3），只加了耗时上报。

**未验证的事，见 §8**：本次改动**尚未部署到实机插件目录**，因此"30 秒计算期间 ADS 可操作""常态 GUI 心跳 < 200ms"这些实机指标没有在真实 ADS 里测过；我们只做了实机**只读核查**（确认现场确实有 47.3s 的 `run_python` 在跑，并采到 `/health` 响应 45/4/12ms）。

## 2. 新调用链

### 2.1 长计算（run_compute）

```
LLM tool_call: run_compute{code, inputs, timeout_s}
  └─ agent._run_tool_call
       ├─ job_id = uuid4().hex            ← 派发前生成
       ├─ Turn.register_job(job_id, kind="compute")
       └─ Turn._run_compute_tool(args, job_id)
            ├─ _get_compute_manager(cfg)           后端进程级单例
            ├─ manager.submit(job_id, code, inputs, timeout_s)
            │    ├─ 锁内: 幂等检查 → 排队容量 → 建 record → 写 request.json
            │    ├─ _probe_env(): 缺 numpy/scipy → ComputeEnvError（绝不静默换解释器）
            │    └─ 入队
            ├─ dispatcher 线程按 max_workers 取作业
            │    └─ _spawn: python compute_worker.py <job_dir>
            │         stdout/stderr 直写 log.txt 文件句柄（**无管道，不存在写满死锁**）
            │         Windows creationflags=0x08000000（隐藏窗口）
            └─ manager.wait(job_id, timeout_s, cancel_check=turn.cancelled)
                 └─ 终态后 _compute_result_from_record() → {ok, state, result, partial, ...}
```

`compute_worker.py` 内部：读 `request.json` → 建命名空间 `inputs` / `check_cancel()` / `progress()` / `emit_result()` → `exec` 用户代码 → 结果 `_sanitize` 成 JSON（ndarray → list，nan/inf → str，>500 项加 `__截断__`）→ 原子写 `result.json` → `os._exit(0)`。看门狗 `threading.Timer(timeout_s)` 到点写 `state:timed_out` 并 `os._exit(9)`（纯 C 热循环也能退）。

**数据传递协议（明确不用 pickle 传活对象）**：输入只有 `inputs`（JSON 可序列化）+ `code`；输出只有 `result` 变量或 `emit_result()`。**不传 ADS Design / Workspace / Qt 对象 / 任何原生句柄**。`run_python` 的常驻 `_PY_ENV` 不会被 worker 继承——旧脚本必须显式传数据（`test_run_python_boundary.py::test_persistent_env_and_helpers_survive_ctx_plumbing` 锁住了 run_python 侧的兼容性，worker 侧的隔离由 `test_compute_worker.py::test_inputs_are_explicit_and_isolated_between_jobs` 锁住）。

### 2.2 停止（用户点"停止"）

```
panel._stop_run()
  ├─ ChatWorker.stop() → 置 _stop 标志 + daemon 线程 POST /chat/cancel{turn_id}
  │    └─ finally: _release_socket()   ← 主动关本地 socket，读线程立即收工
  └─ QTimer.singleShot(1000, _stop_followup)   ← 一秒后仍无结论就改文案

backend POST /chat/cancel
  ├─ turn.cancel()                     置轮次取消事件
  ├─ cancel_info = turn.propagate_cancel()
  │    ├─ 计算作业 → compute_manager.cancel(job_id)
  │    │    queued  → 直接 cancelled（reason=queued_cancelled_before_spawn，绝不 spawn）
  │    │    running → 落 cancel_requested → 写 stop 标志 → 宽限 3s
  │    │              → terminate → taskkill /T /F（仅自有 pid）→ _finalize
  │    └─ ADS 作业 → tools_mod.cancel_ads_jobs() → 工具服务 /cancel
  └─ _push_turn_event({type:"cancel_requested", jobs:cancel_info})   ← SSE 即时可见
```

面板收到 `cancel_requested` 后显示"⏳ 已请求取消：N 个排队作业已取消（未执行）/ N 个 ADS 作业仍在执行，会在安全边界收尾 / N 个计算作业已停止"，**与 `cancelled` 事件的"已停止"明确区分**。

`run_python` 的取消边界（如实、不假装能中断）：

| 边界 | 行为 |
|---|---|
| `before_exec` | 一行用户代码都不跑，返回 `cancelled:true, cancel_boundary:"before_exec"` |
| `after_exec` | 脚本已在 ADS 主线程执行中，**无法安全中断**；结束时如实追加"[取消边界] 收到停止请求时脚本已在 ADS 主线程执行中；无法中断，直到本次调用结束（N.Ns）才停止。此前的写入已发生，请以设计实际状态为准。" |

**刻意不做跨线程注入异常**：那会在 ADS 数据库操作中途抛进半写状态，比卡住更糟。这是设计取舍，不是遗漏。

### 2.3 仿真（hpeesofsim 子进程）的取消与执行预算

`keysight.edatoolbox` 的 `CircuitSimulator.run_netlist()` **既没有 timeout 参数，也没有 cancel 方法**：它最终落到 `util.execute` 里的一句 `subprocess.check_call`，同步阻塞、无法中途打断。所以能取消不是靠"SDK 支持"，而是本插件自己接管了子进程：

```
ads_ops._simulate()
  └─ class WorkspaceSimulator(eda.CircuitSimulator)
       └─ _execute()   ← 唯一能拿到 hpeesofsim pid 的挂点
            ├─ 沿用父类合并好的 env（self._env + extra_env）+ 注入 ADSlibconfig
            ├─ _spawn_sim_child(): subprocess.Popen(stdout/stderr→文件, 不用管道)
            ├─ 登记 _SIM_PROCS[job_id] → /health 与取消都能看见
            └─ 等待循环：
                 ├─ 预算到（sim_timeout） → _ctx_phase("sim:budget_expired") → _terminate_sim_tree → _SimStopped(timed_out)
                 ├─ ctx.cancelled()       → _terminate_sim_tree → _SimStopped(cancel_requested)
                 └─ 退出                  → rc==0 继续；rc!=0 抛 ExecutionError（保持 SDK 语义）
```

* `_terminate_sim_tree()`：先 `terminate()`，宽限期内没退才 `taskkill /T /F /PID <自己的 pid>`。**绝不按进程名批量杀**，用户的 ADS 宿主与其它仿真不受牵连。
* 判活用 ctypes `OpenProcess` + `GetExitCodeProcess`（259 = STILL_ALIVE）。**绝不用 `os.kill(pid, 0)`**：Windows 上第二个参数是退出码，会直接把目标进程 TerminateProcess 掉。
* 被自己终止时不抛 `ExecutionError`（那是"hpeesofsim 自己失败"的语义），而是抛 `_SimStopped`，`_simulate` 据此返回 `status="cancelled"|"timed_out"` + `partial=True`，并带 `stopped{outcome, returncode, pid, budget_s}`。
* 工具服务 `request_cancel()` 对**执行中的仿真**会立即调 `ads_ops.cancel_sim_process()` 踢一脚，而不是等下一轮轮询才发现取消标志（拿的是 `sys.modules` 里已加载的模块，避免热重载把 `_SIM_PROCS` 换成空表导致"取消不到正在跑的进程"）。
* 输出写文件不写管道，所以大量 stdout/stderr 不会因写满而互锁。

## 3. 接口契约

### 3.1 身份

| 字段 | 含义 | 产生位置 |
|---|---|---|
| `turn_id` | 一輪对话 | 面板 `ChatWorker.__init__`（uuid4.hex）/ 后端 `_new_turn_id()` |
| `job_id` | 一次工具作业 | **派发前**由 `agent._run_tool_call` 生成（uuid4.hex），登记进 `Turn._active_jobs` |
| `request_id` | 幂等键（模型导入端点） | `server.py` `_IDEM_CACHE`（TTL 24h，max 500），本次未改 |
| `workspace` | 工作区标识 | `compute_manager` record 字段 |
| `design_fingerprint` | 设计版本 | `ads_ops.design_fingerprint` 工具，本次未改 |
| `worker_pid` | 计算子进程 pid | `compute_manager._dispatch_one` 记录；`/health` 可见 |

### 3.2 作业状态

```
queued → running → (cancel_requested) → succeeded | failed | cancelled | timed_out
```

必须区分的四件事（都在测试里锁住）：

| 概念 | 表现 |
|---|---|
| 客户端等待超时 | `manager.wait()` 返回**非终态** record；随后 `inspect()` 仍是 `running` |
| 执行预算到期 | `state=timed_out`，`exit_kind=natural`（worker 自己 `os._exit(9)`）或 `terminated`（管理器兜底），`error` 含"预算" |
| 已请求取消 | `state=cancel_requested`，`Turn.current_jobs()` 里仍在（"取消成功"≠"已退出"） |
| worker 已实际退出 | 终态 + `end_ts`/`elapsed_s`/`exit_kind`；`_pid_alive(pid)` 为假 |

`exit_kind ∈ natural | terminated | crashed | missing`；`error_kind` 如 `timeout` / `cancelled_by_request` / `cancelled_by_manager` / `crashed_exit_<rc>` / `backend_restart` / `request_unreadable`。

### 3.3 作业接口（`backend/compute_manager.py`）

```python
ComputeManager(base_dir=None, python_executable=None, max_workers=2,
               queue_capacity=8, default_timeout_s=600, max_timeout_s=7200,
               cancel_grace_s=3.0, probe_cache_s=3600)
submit(job_id, code, inputs=None, timeout_s=None, workspace="", label="") -> record dict
inspect(job_id) -> record dict
collect_result(job_id) -> record dict
wait(job_id, timeout_s, cancel_check=None) -> record dict（可能是非终态）
cancel(job_id) -> {"ok","state","requested","reason"}
snapshot() -> {"available","max_workers","queue_capacity","running","queued",
               "cancel_requested","jobs":[...],"python_executable"}
shutdown_all(grace_s=None)
```

异常：`ComputeError` / `ComputeQueueFull` / `ComputeBusy`（保留）/ `ComputeEnvError`。

### 3.4 结果结构

```json
{
  "ok": true/false, "state": "...", "job_id": "...", "worker_pid": 1234,
  "elapsed_s": 0.81, "exit_kind": "natural", "error_kind": null,
  "result": {...}, "partial": false, "stdout_tail": "...",
  "error": "..."
}
```

**部分结果 vs 完整结果**：`partial=true` 表示结果被截断（>256KB）或作业中途被取消/超时。`succeeded` + `partial=false` 才是完整结果。**被取消的作业绝不会报 `succeeded`**——这是本轮修掉的一个真实缺陷（worker 原先只要脚本留下了 `result` 变量就报成功，见 §7）。

### 3.5 并发与资源规则

| 项 | 默认 | 配置键 |
|---|---|---|
| 计算 worker 并发 | 2 | `[agent] compute_max_workers` |
| 计算排队容量 | 8 | `compute_queue_capacity` |
| 执行预算 | 600s（硬顶 7200s） | `compute_timeout_s` / `compute_max_timeout_s` |
| 取消宽限期 | 3.0s | `compute_cancel_grace_s` |
| 解释器 | `sys.executable` | `compute_python`（空=自动） |
| 作业目录 | `<data_root>/compute_jobs` | `compute_base_dir` |
| 工具排队容量 | 64 | `[agent] tool_queue_capacity` |
| pump 单次作业数 | 16 | `pump_max_jobs` |
| pump 软时间预算 | 8ms | `pump_time_budget_ms` |
| 活跃作业上限 | 4 | `active_job_limit` |
| GUI 心跳间隔 | 200ms | `gui_heartbeat_ms` |
| stdout/stderr 尾部 | 256KB | 常量 `_LOG_TAIL_LIMIT` |
| 结果大小上限 | 256KB（超出标 partial） | 常量 `_RESULT_LIMIT` |
| 终态历史 | 256 条 / 管理器的 `manager.log` 1MB 封顶 | 常量 |

**生命周期清理**：作业终态后 `_cleanup_job_dir` 删 `log.txt`/`progress.jsonl`/`request.json`/stop 标志，**保留 `state.json`**（供重启后解释）。后端启动时 `_sweep_stale_jobs()` 扫描：有终态标记的加载回内存；既无标记也无请求的目录直接删（不造假）；其余标 `failed` + `error_kind="backend_restart"` + `error="后端重启，作业状态未知"`。**绝不追杀历史进程**。

## 4. `/health` 的三层可见性

| 层 | 字段 | 位置 |
|---|---|---|
| HTTP 服务是否可达 | `status` / `service` / `identity` | 两端都有 |
| GUI 心跳是否新鲜 | `gui_heartbeat_age_ms` / `heartbeat_stale` | ADS 端 `toolserver /health`（**独立 QTimer，不依赖 pump**） |
| 排队 / 执行中 / 取消中 | `queued` / `busy_count` / `jobs[]` / `cancelling_count` / `cancel_requested_count` / `timed_out_count` / `active_limit` / `finished_recent` | ADS 端 |
| 计算作业（不经过 ADS GUI） | `compute: {available, running, queued, cancel_requested, jobs[], max_workers, queue_capacity, python_executable}` | **后端** `/health`（本轮新增） |

`heartbeat_stale` 只说明**主线程疑似阻塞**（阈值 `max(2000ms, 4×间隔)`），不直接断言死锁——因为它也可能只是主线程在跑一个合法的短工具。

## 6. 主线程优化：做了什么、没做什么

### 6.1 数据集路径（已做）

`read_traces` / `read_dataset` 每个表达式都会 `block.to_dataframe().reset_index()`，同一数据块被多个表达式命中时成倍放大。改为**按块名缓存**（`_df_cache`），配 2 个行为测试锁住"每块只物化一次"。

### 6.2 会话保存与活动行（已做）

| 修改 | 前 | 后 |
|---|---|---|
| 活动行刷新 | `chat.clear()` + 遍历全部 entries 重建 + 同步全量保存 | 就地 `refresh()` + `reflow()`；找不到行才回退重建 |

## 7. 本轮修掉的真实缺陷（都是自己写出来又抓回来的）

| 缺陷 | 现象 | 修法 |
|---|---|---|
| 协作式取消报"成功" | worker 只要脚本留下了 `result` 变量就 `state=succeeded, partial=false`——违反"部分结果不得标成完整成功" | worker 侧：`stopped = os.path.exists(stop_path)`，`succeeded` + stopped → `cancelled` + `cancelled_by_request`，结果保留但强制 `partial=true`。agent 侧：`cancelled`/`timed_out` 交回 `result` 时一并置 `partial=true` |
| 强制终止被误报成崩溃 | watcher 与 `cancel()` 竞态，一次真实的 `terminate` 落成 `failed/crashed/error:"worker 异常退出（rc=1）"` | 新增 `_killed` 集合，`cancel()` 在 `_terminate_tree` **之前**标记，`_finalize` 优先按 `killed_by_manager` 归类 |
| pump 在极小预算下饿死队列 | `executed==0` 时就做预算检查，0.001ms 预算 → 第一个作业都启动不了 | 改成 `executed > 0 and ...`：本 tick 至少推进一个作业 |
| `UnboundLocalError` 崩掉整个工具调用 | ADS 分支 `finally` 在 `result` 未赋值时读取 | `result = None` 预置 + `isinstance` 保守判断 |
| 测试替身的 `yield` 让整个用例假通过 | `_FakeTools.call` 带 `yield` → 变生成器 → `"error" in result` 只创建对象不执行函数体 | 删 `yield`，真实 `return` |
| 后台线程异常被吞，测试仍 PASS | 容量用例的后台 `TimeoutError` 不影响 rc | `_harness` 导入即装 `threading.excepthook`，收尾有异常直接判 FAIL |

## 10. 剩余限制（如实列出）

1. **ADS 原生调用不可中断**：`run_python` 一旦进入 `exec`、建图一旦进入 ADS 数据库写入、仿真的 `generate_netlist()` 阶段（仍在主线程、仍要访问 DE 数据库），都无法安全打断。跨线程注入异常会留下半写 design，我们**明确不做**。可做的是：限制入口规模、记录阶段（`set_phase`）、如实显示取消边界、不承诺立即停止。`run_python` 现在会打印"[主线程占用] 本次在 ADS 主线程执行了 N.Ns"，`>5s` 还会提示改用 `run_compute`。
   **仿真已不再是"完全不可取消"**：`_execute` 之后 hpeesofsim 是本插件自己 `Popen` 的子进程，取消与执行预算都能真正终止它（见 §2.3）。但**网表生成阶段仍不可中断**，且 SDK 本身不提供任何 timeout/cancel 参数——这个能力是我们自己接管子进程实现的，不是 SDK 的能力。
2. **进程隔离不是安全沙箱**：`run_compute` 的子进程拥有完整权限（文件、网络、任意 import）。它解决的是**资源隔离与可回收性**（超时/取消后整进程回收），不是安全边界。`compute_worker.py` 的 docstring 里写明了这一点。
3. **布局/走线在大图上仍占主线程**：≥50 级规模 0.4~1.9s（chain51 布局单项 5.1s）。搬去 worker 需要把 `build_schematic` 拆成规划/应用两阶段并做设计版本校验，属架构改动，本轮未做。已加 `layout_ms`/`wire_ms` 上报。
4. **布局存在既有非确定性**（本次未引入、未修复）：`auto_layout_positions` 多处遍历 `set` 决定摆放顺序，同一设计在不同进程（`PYTHONHASHSEED` 不同）可能得到不同的 annot 偏移/个别坐标。实测 seed 0/1/2/4/5 → `T01.x=4.95`，seed 3 → `6.35`；HEAD 版本同样如此。修它属重构级改动且会改变用户已建图的输出，因此只记录，由 `test_layout_golden.py` 用固定种子兜住。
5. **实机验收未完成**：见 §9。需要把工作区改动部署到插件目录后重跑验收脚本。
6. **两个既有测试失败**：见 §8.2，都属用户既有改动或环境残留，未擅自修。

## 12. 用户操作说明（简明版）

**什么时候用 `run_compute`**
- 数值优化（`scipy.optimize.minimize`）、曲线拟合、大规模参数扫描/搜索、纯文件数据处理 → **一律用 `run_compute`**。
- 写法：把数据放进 `inputs`，用 `result = ...` 或 `emit_result(...)` 交回结果。想中途停就每隔一段时间调一次 `check_cancel()`。
- 它**不能**访问 ADS 对象（Design/Workspace/网表都拿不到）。要读 ADS 数据，先用 `read_dataset`/`read_traces` 取出来，再喂给 `run_compute`。

**什么时候用 `run_python`**
- 只在预置工具覆盖不到、且**几秒内能跑完**的 ADS 对象操作。
- 它在 ADS 主线程同步执行，**无法中途中断**。超过 5 秒会打印"[主线程占用]"提示。

**怎么停**
- 点停止 → 面板先显示"已请求取消：N 个排队作业已取消（未执行）/ N 个仍在执行"。
- 排队中的作业**一行代码都不会跑**；正在跑的会被请求停止，计算作业通常几秒内退出；**仿真正在跑 hpeesofsim 时会被真正终止**（先 `terminate`，宽限 `sim_cancel_grace_s` 内没退才结束整棵自有进程树），返回 `cancelled` + `partial=true`；ADS 原生调用会跑到当前这次调用结束才停（此前的写入已发生，以设计实际状态为准）。
- `HTTP 请求结束` ≠ `执行结束`：点了停止之后仍可用 `/health` 查真实状态。
- 仿真的**网表生成阶段**（`generate_netlist()`，要访问 DE 数据库）仍不可中断；要缩短这一段只能减少单次仿真的规模。

**怎么看健康**
- ADS 端 `/health`：`gui_heartbeat_age_ms` 变大 = 主线程疑似阻塞；`queued`/`cancelling_count`/`finished_recent` 看排队与收尾。
- 后端 `/health`：`compute.running` / `compute.queued` / `compute.jobs[]` 看计算作业。
