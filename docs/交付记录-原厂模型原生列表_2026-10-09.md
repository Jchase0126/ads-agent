## 1. 结论摘要

**核心目标已达成并实机验证**：导入原厂 Design Kit 后，其原厂分类**确实已注册进 ADS 原生元件列表**（这是本轮最重要的实机发现），本插件现在能**程序化确认并定位**这些分类，并在面板上新增「在 ADS 元件列表中打开」动作。

**一个必须如实的硬限制**：本机 ADS 2027 **没有任何 API 能程序化打开/置前 Component Palette 或 Component Library 窗口**。因此功能落到一个诚实的主路径 `outcome="located"`：**能定位到真实分类，但窗口开不了**，并给出人工入口的准确菜单路径 —— 而不是假装点开了。

**本轮未做**：完整用户流程的后半段（真实放置元件 → 选择料号 → 补齐 Include/依赖 → 真实仿真 → 重开/幂等/卸载），以及历史故障复查（TDK include/PDK 映射、DUT1.3/DUT2.3 引脚、网表 `unexpected ':'`）。见 §7。

## 2. 现有可复用能力 vs 实际缺口（实施前盘点）

**可复用**（未重造）：
- 导入链已完整：上传 → 扫描识别 → 解压 → 建索引 → `attach_design_kit`（写工作区 `lib.defs`，含幂等/同名冲突/只读回退/取消回滚）。本轮**未改动其挂接语义**。
- `list_vendor_models` / `get_vendor_model_info` / `validate_model_import` 已能枚举元件、读真实参数与引脚、做可选真实仿真。
- 证据体系（`model_validation`）已具备唯一键、变体/参数/文件指纹、staleness 失效。
- 测试脚手架（`_harness` 隔离、假 ADS 工具服务、Qt 离屏）齐备。

**实际缺口**（本轮的靶子）：
- **全工程没有任何打开/定位原生 Palette 或 Component Library 的代码**。`panel._attach_view` 只做"拉清单 + 就地展开文字"，`_models_text` 是截断的纯文字索引 —— 都不是原生列表。
- 挂接成功只到 `pending_verify`，**没有任何一步能回答"分类注册了没有"**。
- 静态层完全不知道 Design Kit 的 palette 资源（eesof_lib.cfg / BOOT_AEL / palette / bitmaps / 浏览器控制文件）长什么样。

## 4. 交付物（修改文件及原因）

### 4.1 静态检测（`backend/model_store.py`）
新增 `_parse_eesof_cfg` / `_nl_is_external` / `_nl_resolve` / `_scan_native_list`；
`scan_archive` 结果新增与 `library_attach` 同级的 **`native_list`** 键：
`eesof_lib_cfg / boot_ael / palette_ael / atf / bitmaps / browser_ctl / lib_defs / data_paths / design_kit_name / version / tech_desc / has_palette_assets / evidence / limits`。

- **原因**：让"这个包能不能有原生面板"在解压后即可判定，并为运行期定位提供资源清单。
- 路径口径：cfg 值解析时相对 `eesof_lib.cfg` 所在目录，**返回值为「包根相对」posix 路径**（与既有 `plan`/`lib_defs_paths` 同口径）。
- `BOOT_AEL` 值不带扩展名 → 按 `原样 → .ael → .atf` 探测，命中即登记。
- 指向包外（`$VAR`/`%VAR%`/绝对路径）或越出包根的段 → 记入 `limits` 并留空，**不猜**。

### 4.2 ADS 侧工具（`addon/ads_agent/model_ops.py`）
新增 `open_vendor_palette`（注册进 `HANDLERS`）+ helpers `_ael_item_def` / `_ael_vpn` / `_ael_context_window` / `_read_eesof_lib_cfg` / `_resolve_cfg_asset` / `_probe_library_cfg_vars` / `_probe_ael` / `_focus_library_window`。

- 返回结构（键名冻结）：`outcome / boot{eesof_lib_cfg, boot_ael, loaded, loaded_basis, palette_groups[], registered_components, control_files, config_vars, evidence} / native{component_library, palette, located{found, library, category, library_found, via, window}} / palette_api / limits / verified / steps`
- `boot.loaded` 三态：命中 → `True`；双探测都成功执行且都为空 → `False`；探测本身不可用 → `"unknown"`（**绝不猜**）。
- `boot.palette_groups`：遍历 `lib.cells`（上限 2000）按 `deitem_get_visible_palette_name` 返回的真实分组名聚合。
- **只读**：不改工作区/不加删库/不放置元件/不保存/不改全局 Favorite/不执行 `.atf`。

### 4.3 后端契约
| 文件 | 改动 | 原因 |
|---|---|---|
| `backend/tools.py` | `TIMEOUTS["open_vendor_palette"]=240` + JSON schema（**不含任何路径参数**） | 漏登记会判"未知工具"（历史事故） |
| `backend/model_tools.py` | `open_vendor_palette()`：先取**可信** `current_workspace` → 按 `package_id` 解析 `kit_root` → 派发；新增 `AdsUnreachableError` | LLM/面板传的路径一律不采信 |
| `backend/server.py` | 新增 `POST /models/open` | 面板直达，**不经 LLM** |
| `backend/model_validation.py` | `STAGES` 5 → **7 阶段**（+`booted` 库已加载启动配置、+`listed` 原生列表可见）；`package_summary` 修**漏桶** | 需求 §5 要求的新证据维度 |
| `backend/model_orchestration.py` | `_interpret_attach` 成功分支加 `step="native_list"` + `result.native_list` 可执行提示 | 让面板知道可打开 |

### 4.4 面板（`addon/ads_agent/model_attachments.py`、`panel.py`）
新增按钮「在 ADS 元件列表中打开」：显示条件 = `package_kind ∈ {design_kit, mixed}` **且** `state ∈ {pending_verify, ready}` **且** 有已挂接库。
`panel._attach_open` 走后台线程 `POST /models/open`（复用既有 `_spawn_model_worker`），回调渲染 `boot.loaded` / `registered_components` / `palette_groups` 数 / `native.*` / `limits`。「查看包清单」**保留**为诊断动作。

## 5. 实机验收结果（ADS 2027 真实运行，只读）

测试包：`E:\ADS\Work_AI\tdk_library_for_ads_v2019.10.zip`（v2019.10，4630 条目）
目标库：`TDK_Component_Library_v2019.10`（只读挂接于 `E:\ADS\Work_AI\BFR106_wrk`）

**加载方式**：内存热注入（`patched_via=inject`，未改任何磁盘文件）。**注意**：工程原有的 mtime 热重载实测**形同虚设** —— 它只在 `_active_jobs` 为空时执行，而请求派发期间恒非空，故改动 `model_ops.py` 必须重启 ADS 或注入。已写入 `MEMORY.md`。

| 字段 | 实测值 |
|---|---|
| `outcome` | `"located"` |
| `boot.loaded` | `True`，`loaded_basis` 含 `dm_find_item_definition(...)='TDK_Component_Library_v2019.10:TDK_Netlist_Include'` 与 `deitem_get_visible_palette_name(...)='TDK Chip Beads'` |
| `boot.registered_components` | `416` |
| `boot.palette_groups` | **10 组**，每组 items 与独立基准**完全一致** |
| `native.located` | `found=True`、`via="deitem_get_visible_palette_name"`、`category="TDK Chip Beads"` |
| `verified` | `False`（打开 ≠ 可用） |

**10 个真实原生分类**：TDK Inductors 152 / TDK Multilayer Ceramic Chip Capacitors 171 / TDK Common Mode Filters 27 / TDK 3-Terminal Filters 23 / TDK Chip Beads 22 / TDK Varistors 10 / TDK Pulse Transformers 3 / TDK 3-Terminal Feed Through Multilayer Ceramic Capacitors 3 / TDK Noise Suppression Filters 3 / TDK Multilayer Chip Protectors 2

**416 vs 417 的解释**：库目录 `circuit/ael` 有 417 个 `.atf`，但 `TDK_Common_Data` 不是 ADS cell（`lib.cells` 只有 416），其两个探测均返回 None。416 是"库 cell 数"口径，417 是"目录文件数"口径 —— 工具取前者，如实合理。

**交叉验证（关键）**：用独立探针脚本另行枚举 → `queried=417, group_count=10`，**10 个分组名与 items 与工具输出逐组完全一致** → 证明 `palette_groups` 非编造。

**负例**：指定不存在的分类 → `found=False` 如实降级为 `loaded_only` 并列出真实 10 组；库名不存在 → `not_attached`；workspace 未挂 TDK → `workspace_mismatch`（在任何库逻辑前返回）。

**只读自证**：`lib.defs` 前后 sha256 一致（`2f716e8ab816afadad0f82fa83416ffad35619e988e69197d80284e6f010bb6b`，size 219，mtime 均未变）。

**截图**：❌ 未能提供。因为 ADS 无 API 程序化打开 Palette/Component Library 窗口，无法在无人值守下截图；等价的客观证据是上面的分组枚举 + 交叉验证。若需截图，需人工在 ADS 里打开 `\Insert\Component\Component Library...` 后截取。

## 7. 尚未通过 / 未验证的事项（如实边界）

**本轮明确未做**（需求 §6 的实机验收步骤 3–7）：
1. **真实放置一个原厂元件并打开参数窗口选择料号** —— 未做（本轮验收严格遵守只读纪律）。
2. **用 Agent 确定性工具放置同一元件/料号并核对 master/参数/引脚** —— 未做。
3. **按原厂规则补齐 Netlist Include / 依赖并只读核对网表** —— 未做（TDK 包的 `TDK_Netlist_Include` 分类已识别，但未实际生成/核对网表）。
4. **执行真实仿真并保存网表/日志/数据集** —— 未做。
5. **重开工作区仍能打开列表、重复导入无重复、卸载只移除本次引用** —— 未做。
6. **历史故障复查**：TDK include/PDK 映射缺失、DUT1.3/DUT2.3 引脚复核差异、网表 `unexpected ':'` —— 均**未复查**。
7. **完整用户流程链路**（面板上传 → 导入 → 点按钮 → 面板渲染）—— 本轮实机验收是**直接调用 ADS 侧工具**，未走面板按钮；面板与后端路由由离线测试覆盖。

**已知限制（非缺陷）**：
- 无 API 程序化打开 Palette / Component Library 窗口；`native.palette.opened` 恒 `False`。
- 库浏览器**置前**分支未覆盖（验收时 ADS 未打开 `BROWSER_WINDOW`，`windows=0`）。
- `create_*_palette` 兜底注册路径**未实测写入**（只读纪律下故意未调用）。
- "ADS 重启后免注入即通过"未实测。
- `AdsUnreachableError` 只在 `/models/open` 做了 502 区分；`/models/import` 等端点仍会把"ADS 不可达"报成 409 `no_workspace`（既有行为，未改以免破坏其测试）。

**本轮顺带修复的既有缺陷（非本功能引入）**：
1. **`agent.py:821` 把 `cancel_event=` 传给不接受它的 handler** → LLM 路径调用 `list_vendor_models`/`get_vendor_model_info`/`validate_model_import` **必现 TypeError**。已统一签名为 `(cfg, args, cancel_event=None)`。
2. **`server._read_json` 非法 body 让后端永久挂起**（影响**所有** JSON 端点）：`_drain_body()` 按 `Content-Length` 计算待排空字节却**不减已读部分**，而 `_read_json` 里 body 早已读完 → keep-alive 上阻塞占死线程。已删除该两处多余 drain，现非法 body **立即回 400**。
3. **`_handle_model_open` 的 `except` 顺序**让 502 分支成死代码（`AdsUnreachableError` 是 `ModelToolError` 子类，被先捕获）→ ADS 不可达被误报成"没开工作区"。已调整顺序，现回 502 `ads_unreachable`。
4. **`tests/run_tests.py` 漏标** `test_model_http.py` 的 PySide6 依赖 → 纯 stdlib 下报 1 项失败而非正确跳过。已修。

**既有失败（与本轮无关，属用户未提交在制品，未动）**：
- `tests/test_model_deps_gate.py` 2 项。三重证据判定为既有：① 相关文件 mtime 全部早于本轮；② 失败路径经 `model_gate.compare_model_evidence`，不经本轮改动的 `model_store`；③ 最小复现（不 import 本轮任何模块）成立。**根因是测试断言与其断言对象自相矛盾**：`test:308` 断言 `reuse==True` 而 `model_gate.py:158` 语义是 incomplete 一律不复用；`test:655` 断言 2 次而 `design_service.py:736-749` 的"恢复最佳候选"会多出第 3 次。**建议用户裁定是改测试还是改实现。**
